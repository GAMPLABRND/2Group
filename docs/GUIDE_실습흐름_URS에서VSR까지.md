# 실습 흐름 지침: URS 작성 완료부터 VSR까지

이 문서는 조별 하네스 폴더에서 실습이 어떤 순서로 진행되는지, 각 단계에서 무엇을 하고 무엇이 남아야 하는지를 정한 지침이다.
AI 도구(Codex CLI)에 주는 지시 문장도 여기에 있다. 이 폴더는 Codex 전용 판이다. 산출물은 한국어 보고용 문체로, 방점과 대시 없이 작성된다.

## 1. 전체 흐름

```
1일차  URS 수정 완료 → FRA (중요 URS 선별, 1인 10개 배정)
       → 바이브코딩 [ AI Agent 원샷 빌드(60분) → 개발 서버 QA 테스팅 → 수정 요청 → 개발 서버 확인 ] (반복)
2일차  → FDS 작성 (AI Agent가 현재 상태를 Word 문서로) → DQ Matrix (개인 담당 10개)
       → 구현 완료 → 커밋(AI), 푸시와 배포(사람) → 배포 URL 확정
       → IOQ 테스트 시나리오 작성 → IOQ 테스트 수행 (배포 URL)
       → RTM 작성 → VSR 작성 → 조별 발표
```

| 단계 | 하는 일 | 사용하는 것 | 남는 것 | 완료 기준 |
|---|---|---|---|---|
| 1 URS 작성 완료 | 배정 URS(Word)의 §2, §6, §7.1을 조가 확정한다 | KPBMA-EDU-001-URS 양식 | `docs/urs/*.docx` | 조항 ID가 표에 텍스트로 있고, 6.1 역할과 계정, 6.3 권한 매트릭스가 채워져 있다 |
| 2 바이브코딩 | 원샷 빌드 후 개발 서버에서 QA와 수정 요청을 반복한다 | 하네스(AGENTS.md, harness/, agents/, design.md), `npm.cmd run dev` | 동작하는 앱, `URS_STATUS.json`, `IMPLEMENTED.md`, 추적성, 증거, gaps, PLAN, DECISIONS, CHANGELOG | URS 7.1 전 조항이 구현 상태와 증거를 가지며 `check:harness -- --final`이 통과한다 |
| 3 FDS 작성 | AI Agent가 구현 완료 시점의 현재 상태를 FDS로 쓰고 Word 문서를 만든다 | `FDS를 작성해줘`, `npm.cmd run fds`, `docs/FDS_GUIDE.md` | `docs/FDS.md`, `docs/KPBMA-EDU-00X-FDS_N조_시스템명_v1.0.docx` | FS/DS 행마다 관련 URS가 있고, 구현된 7.1 조항이 모두 연결되어 있다 (`npm.cmd run fds` ERROR 0건) |
| 4 DQ | URS와 FDS를 대조해 설계가 요구를 충족하는지 확인한다 (개인 담당 10개) | FDS 문서, DQ Matrix(xlsx), `docs/DQ_DRAFT.md` | DQR | 담당 조항마다 Pass, Fail, C/P와 FS/DS ID가 적혀 있다 |
| 5 커밋, 푸시, 배포 | AI가 커밋을 준비하고, 조원이 푸시하면 Vercel이 배포한다 | AI 도구(커밋 준비), 터미널 `git push`, Vercel | 배포 URL, 커밋 이력, 버전 태그 | 배포 URL에서 `/api/seed`와 로그인이 된다. 비밀번호가 1234에서 변경되어 있다 |
| 6 IOQ 시나리오 작성 | 시험 항목과 단계를 쓴다 | IOQP TC 양식, `docs/IOQ_DRAFT.md` | IOQP | 차단 규칙마다 비정상 조건 시험(NT)이 있다 |
| 7 IOQ 수행 | 배포된 시스템에서 시나리오대로 시험하고 증빙을 남긴다 | 배포 URL, 구글 시트, 화면 캡처 | IOQR | 전 항목 결과(Pass, Fail)와 증빙이 있다 |
| 8 RTM 작성 | 요구, 설계, 시험을 잇는다 | `IMPLEMENTED.md`, `docs/RTM_INPUT.md`, RTM xlsx | RTM | URS 조항 ID 전부가 한 행씩 있다 |
| 9 VSR 작성 | 결과를 요약하고 잔여 사항을 정리한다 | VSR Word 양식 | VSR | 미구현 항목과 일탈이 잔여 사항으로 정리되어 있다 |

2일 운영 흐름(2026-08-23 확정)과의 대응: 1일차 13:20 URS 수정과 제출, 14:20 FRA(1인 10개 배정), 15:20 1차 구현(원샷 빌드), 16:20 QA와 수정 요청.
2일차 10:25 FDS 작성(AI Agent), 11:00 DQ Matrix, 13:20 구현 완료와 푸시, 배포, 14:10 IOQ 시나리오, 15:00 IOQ 수행(배포 URL), 15:40 RTM과 VSR, 16:15 조별 발표.
시간은 운영 계획이 기준이며, 이 문서는 순서와 완료 기준을 정한다.

## 2. 단계별 절차

### 2.1 URS 작성 완료
- 배정된 URS(Word)를 조에서 확정한다. 하네스가 읽는 절은 §2 범위, §6 사용자 역할 및 권한, §7.1 기능 요구사항이다. 7.2 ~ 7.8은 참고로 읽는다.
- 역할 코드와 한글 명칭(§6.1), 계정(§7.6)은 URS에 적힌 대로 시스템에 반영된다. 조항 ID(URS-F-001 형식)는 표의 첫 열에 **텍스트로** 들어 있어야 한다.
- 완성한 `.docx`를 `docs/urs/`에 넣는다. 그 외 파일(AGENTS.md, agents/, design.md, lib, .env.local)은 만지지 않는다.

### 2.2 바이브코딩 (원샷 빌드 → QA → 수정 요청 → 확인, 반복)

**2.2.1 원샷 빌드 (60분)**
- AI 대화창에 다음 한 줄을 입력한다.

  ```
  하네스 절차대로 URS MVP 빌드를 시작해.
  ```
  (Codex는 AGENTS.md를 자동으로 읽는다. 앱에서 조별 폴더를 열거나 `codex -C . -s workspace-write -a never`로 시작한다. 서브에이전트를 못 쓰는 환경이면 같은 역할을 순차 처리한다.)
- 진행 중 AI의 중간 출력은 영어로 나오고, 최종 보고와 산출물은 한국어 보고용 문체로 나온다. 60분은 목표 시간이며 구현 가능한 조항을 중단하는 시각이 아니다.
  새 세션이 필요하면 `하네스 상태 파일을 읽고 마지막 미완료 단계부터 계속해.`를 입력한다. 질문하고 멈추면 `질문 금지 규칙대로 기본값을 기록하고 계속 진행해.`를 입력한다.
- 끝나면 `npm.cmd run harness:sync`와 `npm.cmd run check:harness -- --final` 결과를 확인한다. 보고에는 실행 방법, 계정표, 구현 요약, 남은 범위, 하네스 판정, 환경 검증 상태, 산출물 위치가 있다.
  `npm.cmd run dev`로 개발 서버를 켠 뒤 브라우저에서 `http://localhost:3000/api/seed`를 한 번 열고, `/login`의 계정 선택 드롭다운에서 계정을 고른다. 아이디와 초기 비밀번호 `1234`가 채워지므로 로그인 버튼만 누른다(비밀번호를 바꾼 계정은 직접 입력).
- 산출물 확인: `IMPLEMENTED.md`, `PLAN.md`, `DECISIONS.md`, `CHANGELOG.md`, `docs/generated/URS_TRACEABILITY.md`, `URS_EVIDENCE.md`, `URS_GAPS.md`.

**2.2.2 개발 서버 QA 테스팅 (공급자 테스트의 역할)**
조가 공급자(개발사)의 테스터가 되어 개발 서버에서 확인한다. 조원은 개인 PC 로도 접속할 수 있다:
조별 개발 환경과 같은 네트워크에서 `npm.cmd run dev` 시작 화면의 Network 주소(`http://192.168.x.x:3000`)를 브라우저에 입력한다.
조별 PC 의 최초 1회 Windows 방화벽 허용(Node.js, 개인 네트워크)이 필요하며, 와이파이가 기기 간 통신을 막는 환경이면 조별 공유 화면으로 QA 한다. 순서:
1. 정상 흐름: 로그인 → 기준정보 등록 → 업무 기록 등록 → 상태 흐름(요청, 승인, 서명) → 조회와 출력. 구글 시트에 행이 생기는지 연다.
2. 역할별 접근: URS의 계정으로 각각 로그인해 §6.3 권한 매트릭스대로 메뉴와 기능이 보이고 막히는지 확인한다.
3. 차단 규칙: URS의 차단 조항(교정 만료, 중복 사용, 음수 재고, 기한 경과, 규격 외 입력 등)을 일부러 위반해 본다. 안내 문구가 URS 원문과 같은지 본다.
4. 감사추적: 위 조작이 감사추적 화면에 남는지, 수정 시 사유와 전후 값이 있는지 확인한다.
5. 화면과 문구: design.md와 다른 모양, 오타, 잘못된 라벨, 불편한 흐름을 적어 둔다.
6. 미구현 항목: 완료 보고의 미구현 목록을 읽고, 수정 요청으로 해결할 것과 URS 개정으로 풀 것을 나눈다.
발견 사항은 조 노트에 "화면, 현상, 기대 동작, 관련 URS 조항"으로 적는다. 하나씩 수정 요청으로 보낸다.

**2.2.3 수정 요청 (AI Agent, 수정 요청 모드)**
한 번에 하나씩, 아래 형식으로 보낸다.

```
수정 요청: [화면 이름]에서 [현상]. 기대 동작은 [URS 조항 ID의 요구]. 고쳐줘.
```
예: `수정 요청: 사용 시작 화면에서 교정 만료 장비가 목록에 보인다. URS-F-010에 따라 선택되지 않아야 한다. 고쳐줘.`
예: `수정 요청: 대시보드의 "사용중지" 카드 숫자가 시트와 다르다. 확인하고 고쳐줘.`
예: `화면 문구 수정: 로그인 화면 제목을 "장비사용기록서"로 바꿔줘.`

AI는 분류(결함 수정, 개선, URS 외 요청)를 첫 줄에 적고, 변경 내용과 확인 방법을 한국어로 답한다. URS에 없는 요청은 "URS 외 요청"으로 표시되며
DECISIONS.md에 URS 개정 대상으로 남는다(FRA와 URS 개정 논의 소재).

**2.2.4 개발 서버 확인**
브라우저를 새로고침해 AI가 알려 준 확인 방법대로 본다. 개발 서버는 코드가 바뀌면 자동 반영된다. `.env.local`이나 설정 파일이 바뀐 경우에만
터미널에서 Ctrl+C 후 `npm.cmd run dev`로 다시 켠다. 해결되지 않았으면 같은 요청에 현상을 덧붙여 다시 보낸다. 해결되면 다음 발견 사항으로 넘어간다.

**바이브코딩 완료 기준**: URS 7.1의 전 조항이 개발 서버에서 동작하고, 대표 차단 규칙이 확인되며, 조항별 코드와 증거가 실제와 일치하고 `check:harness -- --final`이 통과한다.
남은 구현 가능한 항목이 있으면 상태는 `INCOMPLETE`다. 교육 운영상 다음 단계로 이동해야 하면 해당 상태와 사유를 VSR의 잔여 사항으로 인계하되 구현 완료라고 표현하지 않는다.

### 2.3 FDS 작성 (2일차 오전, AI Agent가 공급자 역할로)
- QA와 수정 요청이 끝나고 하네스 최종 게이트가 통과한 상태에서 AI에게 `FDS를 작성해줘`라고 요청한다. AI가 코드의 현재 상태를 읽어 `docs/FDS.md`를 쓰고 `npm.cmd run fds`로 Word 문서
  `docs/KPBMA-EDU-00X-FDS_N조_시스템명_v1.0.docx`를 만든다(목차는 배포된 FDS 양식과 같은 1 ~ 6장, FS/DS 행마다 관련 URS 조항 ID. 상세는 `docs/FDS_GUIDE.md`).
- `npm.cmd run fds`의 검증 결과를 본다: ERROR 0건, "구현 조항 n/m 건 연결"이 m/m이어야 한다. 연결되지 않은 조항이 있으면 `연결되지 않은 조항을 FS 행에 추가해줘`.
- Word에서 문서를 열어 목차 갱신(예)을 누르고, 표지의 검토자와 승인자를 적고, 4.3 소스코드 통제의 저장소 주소와 태그를 확인한다. 조가 내용을 검토한다(공급자 문서를 사용자가 검토하는 단계).
- 이후 코드가 바뀌면 `FDS를 다시 작성해줘`로 버전을 올려(1.1) 다시 만든다(변경관리). 이전 docx는 그대로 두고 새 파일이 생긴다.

### 2.4 DQ (설계 적격성평가)
- 개인 담당 URS 10개마다 FDS(docx 또는 `docs/FDS.md`)의 FS/DS ID가 대응하는지 대조한다. AI에게 `DQ 대조표를 만들어줘 (URS-F-001, URS-F-007, ...)`라고 하면 `docs/DQ_DRAFT.md`가 생긴다.
- DQ Matrix(xlsx)에 결과(Pass, Fail, C/P)를 적고 DQR을 작성한다. 미충족 항목은 사유와 조치(수정 요청, URS 개정, 잔여 사항)를 적는다.

### 2.5 커밋, 푸시, 배포
- 배포 전에 **비밀번호를 1234에서 변경**한다: 각 계정으로 로그인해 비밀번호 변경 화면에서 바꾸거나, 관리자 계정 관리 화면에서 초기화 후 변경한다.
  변경한 비밀번호는 조 노트에만 적는다.
- 커밋 준비는 AI가, 푸시는 사람이 한다. AI에게 요청한다.

  ```
  배포 준비해. 커밋 메시지는 IOQ 대상 버전임을 알 수 있게 쓰고 v1.0 태그를 만들어줘.
  ```
- AI는 `npm.cmd run check:commit`, `npm.cmd run check:harness -- --final`, `npm.cmd run build`로 커밋 범위와 완료 상태를 확인하고 한국어 메시지로 커밋과 태그를 만든 뒤, 조원이 실행할 명령을 안내한다.
  산출물(IMPLEMENTED.md, PLAN.md, SPEC 등)은 함께 커밋된다. AI는 `git push`를 실행하지 않는다.
- 조원이 VSCode 터미널에서 직접 실행한다.

  ```
  git push origin main --tags
  ```
  GitHub 리포에 연결된 Vercel이 자동으로 배포한다(강사가 사전에 연결). 배포 URL을 조 노트와 README에 적는다.
- 배포 확인: 배포 URL에서 `/api/seed` 호출 → 로그인. 실패하면 Vercel 환경 변수 3종과 재배포를 확인한다(SETUP ⑥).
- 버전 고정: 태그 v1.0이 IOQ 대상 버전이다. IOQ의 설치 확인은 배포 URL과 이 버전을 확인한다.
- 이 시점 이후의 코드 변경은 변경관리로 다룬다: 수정 요청 → CHANGELOG 기록 → 재커밋(AI) → 재푸시(사람), 재배포 → 영향받는 시험 재수행.

### 2.6 IOQ 테스트 시나리오 작성
- AI에게 `IOQ 시나리오 초안을 만들어줘`라고 요청하면 `docs/IOQ_DRAFT.md`가 생긴다(시험 항목별 단계, 조작, 기대 결과, 근거 조항 ID, NT 여부).
- IOQP 양식(TC01 설치 확인, TC02 접근통제, TC03 데이터 처리, TC04 감사추적, TC05 전자서명, TC06 리포팅과 전자기록, TC07 백업과 복구)에 옮겨 적는다.
  FRA에서 NT로 표시한 조항은 반드시 비정상 조건 단계를 넣는다.
- 설치 확인(TC01)은 배포 URL, 버전(태그), 환경 변수 3종 존재, 시트 탭 구성을 확인하는 단계로 쓴다.

### 2.7 IOQ 테스트 수행
- 배포 URL에서 시나리오대로 수행한다. 개발 서버(localhost)가 아니라 배포된 주소를 쓴다.
- 증빙: 단계마다 화면 캡처와 구글 시트 행(감사추적 포함)을 남긴다. 결과를 IOQR에 기록한다.
- 실패 시: 일탈로 기록 → 수정 요청 모드로 고침 → 재커밋(AI), 재푸시(사람), 재배포 → 해당 시험 재수행. 재수행 이력을 남긴다.

### 2.8 RTM 작성
- `IMPLEMENTED.md`가 시작점이다. AI에게 `RTM 입력을 정리해줘`라고 하면 `docs/RTM_INPUT.md`(URS 조항 ID ↔ FS/DS ↔ IOQ 항목 ↔ 상태)가 생긴다.
- RTM xlsx에 옮겨 적는다. URS 7.1의 모든 조항 ID가 한 행씩 있어야 하며, 미구현 조항도 상태와 사유를 적는다.

### 2.9 VSR 작성
- VP에 계획한 활동(URS, FRA, FDS, DQ, IOQ, RTM)이 수행되었는지 요약하고, 일탈과 잔여 사항(미구현 항목과 사유, URS 개정 대상, 교육용 단순화)을 정리한다.
  시스템 사용 승인 여부와 조건을 쓴다.

## 4. 조별 폴더에서 지킬 것
- `lib/sheets.ts`, `design.md`, `docs/FDS_TEMPLATE.md`, `scripts/*.mjs`, `.env.local`은 건드리지 않는다. `.env.local`은 공유하거나 커밋하지 않는다.
- 패키지를 추가하지 않는다(`npm.cmd install <이름>` 금지). 다른 PC의 `node_modules`를 복사하지 않는다.
- URS에 없는 기능을 요청할 때는 "URS 외 요청"임을 알고 요청하고, 필요하면 URS를 개정한다.
- 초기 비밀번호 1234는 QA 편의를 위한 것이다. 배포 전에 반드시 바꾼다. 시드 계정 비밀번호는 교육용 단순화(평문 저장)이므로 실데이터를 넣지 않는다.
- 막히면 `docs/RUNBOOK_당일운영.md`의 증상별 처치를 먼저 본다.
