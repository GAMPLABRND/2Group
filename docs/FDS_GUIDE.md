# FDS 작성 모드 (구현 완료 후, Word 출력)

AGENTS.md의 FDS 모드 상세 지침이다. QA와 수정 요청이 끝나 구현이 완료된 시점에, AI Agent가 공급자(소프트웨어개발팀) 역할로
시스템의 **현재 상태(as-built)** 를 기능 및 설계 규격서(FDS)로 쓴다. 결과는 Word 문서(.docx)다.

트리거 문장: **"FDS를 작성해줘"** (같은 뜻: "FDS 작성", "FDS 초안을 만들어줘", "현재 상태로 FDS 써줘").
코드가 바뀐 뒤 다시 요청하면 버전을 올려(1.0 → 1.1) 같은 절차로 다시 만든다.

## 1. 원칙 (세 가지)

1. **목차는 고정이다.** `docs/FDS_TEMPLATE.md`의 1 ~ 6장, 1.1 ~ 4.3절의 번호와 제목을 그대로 쓴다. 절을 빼거나 더하지 않는다.
   3.2절의 괄호 부분만 시스템 고유 기능 영역명으로 바꾼다(예: "3.2 장비 사용 기록 관리 / Equipment Usage Records"). 영역이 여러 개면 3.2.1, 3.2.2 소절(###)로 나눈다.
2. **불필요한 내용을 쓰지 않는다.** 규제 해설, 일반론, 양식 문구, 자리표시, 시험 절차(IOQ), 위험평가, URS 원문 복사를 넣지 않는다.
   FS 행 하나는 구현된 기능 하나를 검증 가능한 문장으로 쓴다(무엇을 입력하면 무엇이 처리되고 무엇이 보이는지, 차단이면 안내 문구 원문).
   해당 기능이 없는 절은 표를 두되 "해당 없음(사유)" 한 문단으로 끝낸다.
3. **모든 규격은 URS에 연결된다.** FS와 DS 행마다 관련 URS 조항 ID를 적는다(여러 개면 콤마). 구현된 7.1 조항은 빠짐없이 어느 FS 또는 DS 행에 나타나야 한다.
   URS에 없는데 구현된 기능(QA 중 추가 요청 등)은 관련 URS 칸에 "URS 근거 없음 (DECISIONS.md n번, 수정 요청 YYYY-MM-DD)"로 적어 DQ에서 구분되게 한다.
   미구현 조항은 1.2 범위에 제외 목록으로 적고(사유는 IMPLEMENTED.md 문장 그대로) 본문에는 넣지 않는다.

## 2. 근거 파일과 읽는 순서

1. `harness/state/URS_STATUS.json`, `IMPLEMENTED.md`, `docs/generated/URS_TRACEABILITY.md`, `URS_EVIDENCE.md`, `URS_GAPS.md`, `PLAN.md`, `DECISIONS.md`, `CHANGELOG.md`.
2. 코드의 현재 상태: `types.ts`, `lib/brand.ts`, `app/layout.tsx`(메뉴), `app/api/**/route.ts`(라우트, 검증, 차단 문구), `app/**/page.tsx`(화면), `lib/audit.ts`.
   문서는 코드를 기준으로 쓴다. PLAN이나 SPEC과 코드가 다르면 코드가 맞다.
3. `docs/urs/*.md`: 조항 ID와 요구 문장 확인용. URS를 다시 분석하거나 요약하지 않는다.
4. `SPEC_A/B/C.md`는 필드명과 상태값 확인에만 쓴다.

## 3. 절별 작성 요령

| 절 | 쓸 것 | 분량 |
|---|---|---|
| 1.1 목적 | 양식 문장을 시스템명, 조, 영문 약어만 바꿔 쓴다 | 1문단 |
| 1.2 범위 | 적용 대상(웹 앱과 구글 시트), 기준 일자와 버전, **미구현 조항 제외 목록**(ID, 요구 요약, 사유) | 1문단 + 목록 |
| 2.1 사용 목적 | URS §2.2를 근거로 3 ~ 5문장. GAMP Category 5 문장 유지 | 1문단 |
| 2.2 시스템 설명 | 브라우저, 서버 API, 구글 시트의 역할 분담과 동작 방식 | 1문단 |
| 2.3 시스템 구성 | 배포 형태(Vercel), 저장소(시트 1개), 접속 경로 | 1문단 |
| 2.4 컴포넌트 표 | 웹 애플리케이션, 구글 스프레드시트, 웹 브라우저(필요 시 Vercel) | 3 ~ 4행 |
| 2.5 전체 업무 흐름 | 화살표 한 줄 + 역할별 흐름 문장 3 ~ 6개 | 1문단 |
| 3.1 접근 관리 | 로그인(계정 선택, 비밀번호), 역할별 메뉴와 화면 차단, 세션, 비밀번호 변경과 초기화, 잠금 | FS 행 |
| 3.2 고유 기능 | 기준정보, 업무 기록의 등록과 조회, 상태 전이(요청, 승인, 반려, 수정 요청), 출력과 문서번호, 대시보드, 알람 | FS 행 (가장 많음) |
| 3.3 데이터 처리 | 필수값, 중복, 범위, 시간 순서 검증, 자동 계산과 판정, 잔량과 상태 갱신 | FS 행 |
| 3.4 전자기록 | 저장 방식(Append-only), 승인 후 잠금, 수정 사유, 무효 처리, 보존 | FS 행 |
| 3.5 감사추적 | 기록 대상 행위, 기록 항목(행위자, 일시, 전후 값, 사유), 조회와 보고서 출력, 수정 불가 | FS 행 |
| 3.6 전자서명 | 서명 시점, 비밀번호 재입력, 서명 항목과 표시(서명자, 일시, 의미) | FS 행 |
| 3.7 인터페이스 | 서버의 구글 시트 API 연동(서비스 계정), 클라이언트와 서버 사이 `/api/*` | FS 행 |
| 3.8 오류처리 | 차단 규칙과 안내 문구 원문, 권한 없는 접근 처리, 서버 시각(KST) 기준, 429 등 오류 표시 | FS 행 |
| 4.1 구성 | 역할별 권한(URS §6.3 매트릭스를 문장 또는 표로), 실행 환경(Next.js, Node, Vercel), 환경 변수 이름 3종(값 금지), API 라우트 목록과 역할 검사 | DS 행 |
| 4.2 데이터 설계 | 시트 탭마다 DS 행 1개: 탭명과 컬럼을 순서대로 | DS 행 |
| 4.3 소스코드 통제 | GitHub 저장소와 브랜치, IOQ 대상 태그(v1.0), 커밋 메시지 규칙, 규격 코드 해시 확인 | DS 행 2 ~ 3개 |
| 5 데이터 | 전자기록 분류(기준정보, 업무 기록, 감사추적, 계정)와 보존 방법 | 1문단 |
| 6 용어 정의 | 본문에 쓴 약어만 | 표 |

- FS ID는 `FS-001`부터 3.1 → 3.8 순서로 문서 전체에서 연속 부여한다. DS ID는 `DS-001`부터 4.1 → 4.3 순서로 연속 부여한다(RTM에는 "FS-001 (3.1)"처럼 절 번호를 붙여 옮긴다).
- 규격 문장은 규격서 평서형("~한다", "~된다")으로 쓴다. 이 문서에 한해 보고체("~하였습니다")를 쓰지 않는다. 방점(·)과 대시(—)는 쓰지 않는다.
- 화면 안내 문구와 상태명은 코드에 있는 한국어 원문을 따옴표 없이 그대로 쓴다.
- 환경 변수 값, 비밀번호, 서비스 계정 이메일, 시트 ID는 적지 않는다(이름만).

## 4. 절차

1. 2절의 파일을 읽는다. `IMPLEMENTED.md`에서 구현과 부분 조항 목록, 미구현 조항과 사유를 뽑는다.
2. `docs/FDS_TEMPLATE.md`를 `docs/FDS.md`로 복사하고 머리말(문서번호, 시스템명, 영문명칭, 조, 버전, 작성일)과 본문을 채운다. 주석과 대괄호 자리표시를 모두 없앤다.
3. `npm.cmd run fds`를 실행한다. 검증이 오류(ERROR)를 내면 `docs/FDS.md`를 고치고 다시 실행한다. 오류 0건이 될 때까지 반복한다.
   경고(WARN) 중 "연결되지 않은 구현 조항"은 해당 조항을 다루는 FS 또는 DS 행에 ID를 추가해 없앤다. 정말 문서화할 기능이 없으면 그 조항을 다루는 행을 새로 쓴다.
4. 생성된 `docs/KPBMA-EDU-00X-FDS_<조>조_<시스템명>_v<버전>.docx`를 Word에서 열고 표, 페이지 나눔, CI, 승인란을 확인한다. Word를 사용할 수 없으면 DOCX 구조 검증만 수행했다고 명시하고 시각 검증을 환경 대기로 남긴다.
5. `CHANGELOG.md`에 한 행을 추가한다(분류 "문서", 요청 요약 "FDS v<버전> 작성", 변경 파일 docs/FDS.md와 docx).

## 5. 보고 형식 (한국어 보고체, 채팅)

1. 생성 파일: `docs/FDS.md`, `docs/<문서번호>_<조>조_<시스템명>_v<버전>.docx`
2. 규격 수: FS n건(절별 건수), DS n건
3. URS 대조: 구현 조항 n/m 건 연결, 연결되지 않은 조항(있으면 ID와 이유), 미구현 제외 조항 n건(1.2절에 기재), URS 근거 없음 행 n건
4. 사람이 할 일: Word에서 열어 목차 갱신(예 선택), 표지의 검토자와 승인자 기재, 4.3절의 저장소 주소와 태그 확인, 검토 후 DQ Matrix 작성으로 진행
5. 코드가 바뀌면 "FDS를 다시 작성해줘"로 버전을 올려 재생성한다는 안내

## 6. Codex 실행

FDS 모드에서는 서브에이전트를 쓰지 않고 오케스트레이터가 직접 쓴다(코드 읽기 → FDS.md 작성 → `npm.cmd run fds` → 수정 반복 → Word 시각 확인). 목표 시간은 15분이다.
